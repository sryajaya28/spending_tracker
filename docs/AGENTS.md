# Working with more than one agent

Rules so two agents (or sessions) on Stiver do not collide. The owner can override any of them in plain words.

1. **Roles (owner, 2026-11-04; updated: Full-stack engineer is the main developer): Full-stack engineer builds all production code on feature branches; Tech-Lead reviews it, is the integrator and maintains the workflow (`docs/WORKFLOW.md`).** An agent that is not sure whether it is Tech-Lead asks the owner
   before merging to `staging`. Only the integrator merges into `staging`, runs `node tools/fold_changes.js`, `node tools/trim_learnings.js` and `node tools/doc_budget.js` (keep the always-read files small), releases to `main` and runs the
   smoke test. Other agents work on `feature/<name>` branches only, rebase on the latest `staging`
   (`git fetch origin staging && git merge origin/staging`), run the affected tests plus `bash tests/e2e/run_all.sh`, then tell the
   owner "ready: <branch>, tests pass, design link, steps". Explicit owner instructions such as "push to staging directly" or a
   hotfix go before this rule; whoever does it tells the other agent.
2. **No shared edit hotspots.**
   - The service worker cache name is stamped at deploy (`tools/stamp_sw.js`, run as the Vercel build command): never edit it.
   - The changelog entry is its own file in `docs/changes/` (see its README); the integrator folds them into `docs/CHANGELOG.md`.
   - `context.md` is edited in the section a change affects, not appended to; keep edits small.
3. **Split by area.** Say which part of the app you are working on before you start; avoid editing the same large file
   (`prototype/app.js`) region at the same time as another agent. If you must, keep the change small and rebase often.
4. **Hand off in writing.** When you stop with work in progress, add a short "state of my branch" note under
   `context.md` section 16 (done / untested / blocked), so the next agent does not re-read the transcript.
5. **Peer review of production code (owner, 2026-11-04).** Full-stack engineer and Tech-Lead review each other's work before it reaches `staging`.
   - **Applies to** changes under `prototype/`, `api/`, `supabase/` or `vercel.json` (and the tests that gate them) that are **not** in the fast lane.
     **Exempt:** fast lane, docs- or tooling-only changes, and an owner-ordered hotfix (the other developer reviews it afterwards, in the next session).
   - **Author:** when the tests pass, send the ready report to the owner and a short message to the other developer
     ("review: <branch> <commit>, request in one line, design link, tests run"). Fix findings on the same branch.
   - **Reviewer:** read `git diff origin/staging...origin/<branch>`, run the affected tests (`node tools/affected_tests.js`) and the new test, and check:
     1. correctness (logic, edge cases, render order, state) and that the new test fails on the old code;
     2. data safety (save/sync mapping, migrations backwards compatible, nothing lost on reload, RLS untouched);
     3. **only for authentication or database changes:** security checks as in the high-risk lane below; for every other change skip this item (the standing rule against committing secrets, `CLAUDE.md` rule 3, still applies);
     4. house rules (`CLAUDE.md`, `learning.md`): i18n strings, `data-act` / `data-form` + analytics event, design match incl. dark and phone, change file;
     5. simplicity (no duplicate helpers, unique global names, no dead code).
     The `code-review` skill (medium) can do the first pass. Reply with `approved <commit>` or numbered findings marked **blocking** or **suggestion**, and the line `Owner-bound asks: all on the Workspace (yes/no)`.
     One round; the reviewer does not push to the author's branch.
   - **Merging:** the integrator (Tech-Lead) merges Full-stack engineer's branch after reviewing it (that is the review). Tech-Lead's own production-code branches need Full-stack engineer's
     `approved <commit>` before Tech-Lead merges them into `staging`. Put `Reviewed by: <developer> approved <commit>` in the ready report.
   - **Nobody answers?** Say so to the owner and ask whether to wait or waive; never approve your own change.
6. **Tool prompts vs workflow approvals.** `.claude/settings.json` allows routine Figma, GitHub, Supabase and Vercel tool calls without a prompt and still asks for irreversible or production-affecting ones. This only removes tool prompts; the owner's approval for a release, the regression summary and peer review still apply, and an agent never uses an allowed tool to get around them.
7. **The wider team (owner, 2026-11-04).** Product Manager, Designer and QA agents work beside the two developers; roles, hand-off formats, the owner's three gates and the session registry are in `docs/roles/README.md`. Developers receive an approved PRD and an approved Figma link, build, then hand to QA; QA, not the developer, runs regression and smoke. Peer review (rule 5) stays.
8. **Main developer (owner, 2026-11-04).** Full-stack engineer does the building; Tech-Lead reviews every non-fast-lane production change before it reaches `staging` (this replaces the two-way peer review of rule 5 while Full-stack engineer is the only builder), integrates and releases. The full agent-to-agent workflow and message formats are in `docs/WORKFLOW.md`.
9. **Review standard (owner, 2026-11-04).** Agents on the same model share blind spots, so a review counts only when it rests on evidence and, for risky changes, on something independent.
   - **Evidence, not opinion.** Every finding cites `file:line`, a failing test, a query result or a reproduction. A finding without evidence is marked "unverified" and cannot block. "Approved" lists what was run (tests, queries, screenshots) and what was not checked.
   - **Risks first.** The reviewer reads the PRD acceptance checks and writes down the risks it expects (data loss, access, privacy, migrations, concurrency, performance at scale) **before** reading the diff or the author's explanation, then checks those plus rule 5's list. Authors send facts (branch, commit, tests), not conclusions.
   - **Tests prove themselves.** The new test must fail on the old code (revert the fix and run it) and the review says so. Machine checks beat opinions: SQL tests, policy-completeness test, real staging runs with real accounts.
   - **Opus / different-model review: big features only (owner, 2026-11-05).** It is used only for a BIG feature or a major change to authentication or the database (household, the sign-in handoff rebuild). A small change, even one touching authentication or the database (a one-line fix, a copy or limit tweak, a single column), gets normal peer review by the Tech-Lead and QA and no Opus session. When in doubt, the Tech-Lead decides and says so in one line.
   - **An Opus review needs the owner's approval first (owner, 2026-11-05).** Before any Opus / different-model reviewer session is started, the Tech-Lead sends the PM a hand-off (what would be reviewed, why it is big enough, expected cost: sessions and minutes); the PM posts a Workspace **decision** (options: Start the Opus review / Normal review only, with pros, cons and a recommendation). Only after the owner answers "Start the Opus review" (a page answer counts) does the Tech-Lead start the session. No answer means normal review only. This applies to every Opus session, including re-reviews of a revised design or code.
   - **High-risk lane, only for MAJOR changes to authentication or the database** (owner, 2026-11-05, to keep token use low). Authentication means sign-in, sessions, the handoff, invites, tokens, passwords. The database means migrations, RLS, functions, triggers. For those: the reviewer session runs on a **different model** from the author when one is available (`create_session` with `model`), a spike or real-system check replaces assumptions about third-party behaviour, and the owner is told the risks in plain words before the release (never an agent's approval alone). **For every other change (UI, copy, docs, tooling, tests, the Workspace page, analytics, normal features without authentication or database changes) there is no security review, no security checklist and no extra security pass: normal peer review and QA only.**
   - **Independence.** Nobody reviews a change to a process or file they wrote (the workflow owner's changes are reviewed by the other developer). Reviewer and author do not edit each other's branch. One round per change; a disagreement is stated once each, then the owner decides with a recommendation.
   - **Measure it.** `learning.md` keeps a line per escaped defect: a bug that reached `staging` or production after a review approved the change (what, why the review missed it, what check would have caught it). If the same kind recurs, tighten this standard or add an automated check.
10. **The PM is the owner's only gateway (owner, 2026-11-04).** Developers, Designer and QA send anything meant for the owner (decisions, links, summaries, approval requests, blockers) to the Product Manager, who sends the owner one digest and relays answers back verbatim with the date. An approval is valid only as the owner's quoted words relayed by the PM (or the owner's own message in your session). Direct contact with the owner is only for emergencies or an unanswered PM after one reminder. Details: `docs/roles/pm.md`, `docs/WORKFLOW.md`. The owner may still talk to any agent directly at any time: the agent acts on it and sends the PM one line (`owner told <agent>: "<quote>"`, date, effect) so everyone stays in sync; the newer owner message wins over an older relayed one.
11. **Stiver Workspace (owner, 2026-11-04).** Post hand-offs, review verdicts, merges, releases, QA reports and spike results to the Workspace feed, and put every item that needs the owner into its "Needs you" tray, as described in `docs/WORKSPACE.md` (the PM batches and creates the items). Never write an answer on the owner's behalf. A release or a production migration still needs the owner's message in a chat.
12. **The owner does not repeat anything (owner, 2026-11-05).** Read the Workspace (`docs/WORKSPACE.md`) at the start of every session and after every gate: decisions and actions the owner answered there, messages from "You", the backlog. A page answer is the owner's approval for gates 1 and 2 and for all decisions and actions; only a release and production migrations also need the owner's message in a chat. Anything the owner tells you in a chat you post, quoted, to the Workspace `messages` (`Owner said: ...`, `kind: "decision"`) so no other agent has to ask again.
13. **The PM sees the owner's messages first (owner, 2026-11-05).** Messages from "You" in the Workspace are addressed to the PM first: the PM reads them at the start of every turn and after every gate and relays them in detail to the agents affected. Treat the PM's relay as the instruction; if it differs from what you read in the feed, ask the PM. A decision or action answered on the page is already the owner's answer. **Release reports show exact contents, never a summary** (`node tools/release_contents.js`, `docs/RELEASES.md`, `docs/WORKSPACE.md` "Releases").
14. **No agent asks the owner anything directly (owner, 2026-11-05).** An approval, a question, a plan or any request for the owner's time in an agent's own session is a defect: the owner would see it only there, and no other agent would. The routes are: (a) a hand-off message to the PM, who posts a Workspace **decision** or **action**; (b) for an emergency only (production down, data loss, security incident): a Workspace message `to: "owner"` (kind `security` or `release`) **and** a copy to the PM. Rules that follow:
    - **If the owner contacts an agent directly** (the owner may always do that), that agent immediately sends the PM `owner told <agent>: "<quote>"` and posts the same to the Workspace (`Owner said: ...`, rule 12).
    - **Every message that asks for approval must also exist as a Workspace decision.** Ready reports and reviews carry the line `Owner-bound asks: all on the Workspace (yes/no)`; answer "no" only with the fix attached.
    - **No plan mode and no question prompts for owner-facing approvals.** An agent does not enter plan mode and does not use the question tool to get the owner's approval (the harness would show the owner a prompt that no other agent sees); the plan goes to the PM as a hand-off. `.claude/settings.json` denies `AskUserQuestion`, `EnterPlanMode` and `ExitPlanMode` for every session of this repository. A session that was started in plan mode must be switched out of it by the owner (the PM puts it on the Workspace as an Action).
    - **Tool permission prompts** (the `ask` list in `.claude/settings.json`, for example SQL on a database) still reach the owner from the harness: tell the PM **before** running such a call so it can be put on the Workspace as an Action with the exact prompt to expect.
15. **Keep token use low (owner, 2026-11-05: "it's too expensive now").** Cost is context size times number of tool calls: every call re-reads the whole conversation, so messages are cheap and long sessions are not. Rules:
    - **No acknowledgements.** Never send a message that only says "got it", "thanks" or "approved, will do". Every message either needs an answer (say so in the first line) or ends with `No reply needed.` A recipient never answers a `No reply needed.` message.
    - **Long findings live in a file.** Review findings, plans and reports longer than about 15 lines go in `docs/reviews/<date>-<name>.md` on the author's branch (or `docs/prd/`); the message is the link plus at most 5 lines (verdict, number of blocking items, the one thing that needs action).
    - **Few, big calls.** Batch independent tool calls in one turn. Read files by range or search, never whole; use `git diff` instead of printing files; no screenshots or image reads unless the visual itself is the question; never dump an event log, a session list or a database collection unless a decision depends on it.
    - **Reviewers read the diff,** not the repository, and use the standard model; the different-model (Opus) reviewer (rule 9) only for big features or major authentication or database changes, never for small changes, and only after the owner approved it.
    - **Fresh sessions.** A session whose context passes about 200k tokens (the owner or PM can see it as slow, expensive turns) finishes its work package, writes a handoff note (`context.md` section 16 or `docs/handoff/<role>.md`) and a new session continues from the note. Do not run one session for days.
    - **Reading lists per role** are in `docs/roles/README.md`: read only those; `context.md` and `learning.md` by section (search the headings, read the section you need), not whole.
    - **Workspace posts are milestones only** (`docs/WORKSPACE.md`); presence is set when a task starts and ends, with no timer.
16. **Message economy (owner, 2026-11-05, after a session review: "token usage burned very quickly").** Measured on 2026-11-05: over 99% of tokens are cached re-reads of the conversation; the PM (about 585k context) re-read roughly 1.1 to 1.7M tokens on every wake, and every cross-session message, even one ending `No reply needed.`, wakes the receiver for a full turn. So:
    - **Report to the gate owner only.** The Full-stack engineer and QA report to the Tech-Lead; the Tech-Lead reports to the PM at gates only (ready for QA, QA result, production done, a failure or a blocker). The PM never relays a status the owner can read on the Workspace.
    - **One message per event, never one per step.** Combine findings, requests and state in a single message; do not send "starting", "phase done" or "noted" messages; do not send a copy to a second agent (a pointer to the file or the Workspace post is enough).
    - **No crossing messages.** Before sending a go/hold/stop instruction, check the latest message you received from that agent's lane; if two instructions can conflict, send only the one from the gate owner.
    - **A PM turn that only forwards a message ends in one line,** not a summary: the owner reads the Workspace.
    - **Hand off at 400k tokens.** The agent writes `docs/handoff/<role>.md` (state, open items, next steps), tells the PM the new session id is needed, and the PM or Tech-Lead starts the fresh session (rule 15, Fresh sessions). The PM session is replaced first when it is the largest.
    - **No repeated pastes.** Deploying several Edge Functions with the Supabase connector pastes the shared file into every call; prefer the Supabase CLI with an owner-provided access token (an owner Action) for multi-function deploys.
    - **Cheaper model for relay roles** (PM, Designer) is allowed with the owner's OK; review and security roles keep the standard model.
17. **Risk-tiered workflow (owner, 2026-11-05).** Every change takes the cheapest workflow that is still safe: Tier 1 (presentation only), Tier 2 (standard), Tier 3 (full, today's process). The minimum tier comes from the files touched (path table in `docs/workflows/README.md`); an agent may raise a tier, never lower it; escalate on discovery. Load only the tier file for your task (`docs/workflows/TIER_1.md`, `TIER_2.md`, `TIER_3.md`). Where this rule and rules 5-9 disagree for Tier 1 or 2, `docs/workflows/` wins.
