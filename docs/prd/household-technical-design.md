# Technical design: household access (for Developer 2's review)

PRD: `docs/prd/household.md` (v2.1 + check 16 change, owner approved). Design v8 answers Developer 2's merged review (his and an independent Opus reviewer's); section 12 maps every finding to where it is fixed.

## 1. Approach
Keep `user_id` = the **household owner's id** on every money row. A member writes rows with `user_id = owner id`, so no existing FK, composite FK `(id,user_id)`, unique index or constraint changes, and the owner's path is identical to today. Not chosen: a new `household_id` on every table (huge migration).

## 2. Schema (all new tables: RLS on, anon revoked)
- `household_members(owner_id, member_id unique, role check in ('editor','viewer'), added_at, pk(owner_id, member_id))`. One household per person; an owner cannot be a member (function check).
- `household_former_members(owner_id, member_id, display_name, removed_at)`: written when someone leaves or is removed, so their name stays on past entries (PRD check 26).
- `household_invites(id uuid pk, owner_id, email text (stored lower-cased), role, invited_by, invited_user_id uuid, token_hash text (sha-256 of OUR random 32-byte join token; null once used, revoked or expired), created_at, expires_at (fixed 7 days after send or resend), status check in ('pending','accepted','revoked','expired'))` + partial unique `(owner_id, email) where status='pending'`. The raw token exists only in the email we send; it is never in `auth.users` (user_metadata/app_metadata) or in any table.
- `invite_attempts(owner_id, email_hash, at)`: one row per **attempt**, success or failure (rate limit, B4). `join_attempts(ip_hash, token_hash, at)`: one row per join or preview call, inserted before any token lookup (J1).
- `household_state(owner_id pk, rev bigint)`: bumped on any change to the household's data or membership (polling, B2c).
- Slice 2: `activity_log(id bigint identity, owner_id, actor_id, actor_name text, entity, entity_id, action check in ('create','update','delete'), summary jsonb, at)` + index `(owner_id, at desc)`, 180-day purge job.
- New columns on `wallets, transactions, categories, budgets, investment_accounts, holdings, holding_events, debts, debt_payments, occasions, recurring_rules`: `created_by uuid`, `updated_by uuid`, `rev int not null default 1`. Every `user_id ... default auth.uid()` becomes `default household_owner()` so an insert that omits `user_id` lands on the owner (B1).
- Personal tables stay personal: `profiles`, `auth_handoffs`, `support_reports`, storage `support-attachments`.
- `profiles.household_status in ('owner','invited','member','former_member')` (default `owner`, set only by definer functions). **`profiles_update` is narrowed (B-3): `revoke update on public.profiles from authenticated`, then `grant update (display_name, default_currency, ai_tagging_enabled, sample_ids, language, theme, period_day)`** (column list confirmed against `cloud.js` before migration 2); `household_status` is not writable by any client. SQL test: an authenticated PATCH of `household_status` is rejected.

## 3. Functions (S1: all security definer, `set search_path = ''`, fully qualified, `revoke execute from public, anon`, grant only to `authenticated`; email handling uses `lower(email)` text, no citext)
`household_owner()` (caller's owner id; self if owner), `is_writer()` (owner or editor), `household_profile()` (returns only whitelisted columns of the owner's profile: currency, period_day, sample flag, language default; `profiles` itself stays self-only, B6), owner-only RPCs `set_member_role`, `remove_member`, `revoke_invite`, member RPC `leave_household`. **Service-role-only definer RPCs** (`revoke execute ... from authenticated`, SQL test): `create_invite(...)` (cap check + existence check + insert, one transaction with an advisory lock on the owner, S-13) and `delete_user_sessions(user_id)` (deletes `auth.sessions` and the matching `auth.refresh_tokens`, test that none are left, S-12). **`household_owner()`, `is_writer()` and the Edge Functions treat `invited` and `former_member` as no access (B-2).** `household_owner()` for members also requires the caller's session row to exist; it **fails closed**: if `auth.sessions` or the `session_id` claim is missing or unreadable, members get no access (the app shows the no-access page), never access; owners and solo users do not depend on it (T3). A SQL test fails if `auth.sessions` or the claim disappears in an upgrade.

## 4. RLS (B1)
On **every** public table that has a `user_id`: select `using (user_id = (select household_owner()))`; insert/update/delete add `and (select is_writer())` (`with check` the same). Wrapped as initplans: evaluated once per query, no per-row function calls; the owner path equals today's. Migration 2 replaces **all** policies, found by looping `pg_policies` (not only the five in `0002`): `recurring_rules` (4 separate policies on bare `auth.uid()`), portfolio, debts, occasions, `manual_prices`, etc. **SQL test:** loops `pg_policies` for every public table with a `user_id` column and fails if any policy still uses plain `auth.uid()` or a per-row function.
Views and functions (B6): `household_people()` is a `security definer` **function returning a table** (not a view, which trips the Supabase `security_definer_view` advisor), filtered inside by `household_owner()`, including `household_former_members` (B7), and tested to return zero rows for non-members; `spending_by_category`, `budget_status`, `portfolio_history` keep invoker rights and replace `auth.uid()` with `household_owner()`; `wallet_balances`/`debt_balances` stay `security_invoker` and follow RLS.

## 5. Invite lifecycle and join (B-1 to B-5, S-6 to S-14, T1 to T5)
**Principles.** (1) The join token is a secret that exists only in the email we send. GoTrue's own invite mail is **not** used (F2: its token is burned by a public sign-up and anything in invite `data` is readable by any session of that user). (2) A session of the invited user, even one an attacker obtained through a public sign-up (F2), has **no** access and no powers until `join-household` succeeds. (3) Membership is created only by `join-household`, and every call to it presents the token.

### 5.1 `invite-member` (Edge Function, service role stays inside it; restrictive CORS: stiver.io, staging, preview hosts)
1. `auth.getUser(jwt)`; the caller must have `household_status = 'owner'` (not `invited`, `member` or `former_member`) and no membership. No role is ever read from user_metadata.
2. **Insert an `invite_attempts` row first**, then rate-limit: 10 attempts/hour per owner, and a **global** cap per target email (3/day across all owners, S-10), counted before any existence lookup (N7).
3. Validate and lower-case the email; generate a random 32-byte token and its SHA-256; call the definer RPC `create_invite(owner, email, role, token_hash, expires_at = now() + 7 days)`: advisory lock on the owner, member cap (accepted + pending <= 5), existence check (a confirmed `auth.users` row for the email, or any member, returns one generic error: PRD check 2 copy), pending invite returns "Already invited"; inserts `household_invites` (status `pending`). Cap check and insert are one transaction (S-13).
4. `auth.admin.generateLink({type:'invite', email})` creates the unconfirmed auth user **without sending any mail** and with **nothing secret in user_metadata/app_metadata** (at most nothing at all). `handle_new_user` fires now: because a pending invite exists for `lower(new.email)` (looked up in the DB, never from metadata) it creates the profile with `household_status = 'invited'` and **skips seeding** (B-2, F1). The function stores `invited_user_id` on the invite.
5. **Our own sender** (the same Edge Function, Resend API key as a function secret entered by the owner in the dashboard) sends the mail with fixed product wording (subject and body are ours, not user text), in the owner's language: "<owner display name> (<owner email>) invited you to a household on Stiver as Editor/Viewer", showing the inviter's email (S-10), one button to `https://<site>/join#t=<token>`. `inviter_name` is sanitised (markup stripped, 40 chars) and never used in the subject.
6. If `generateLink` or the send succeeds but the call times out, the invite is treated as pending and a reconcile job re-checks it; the row is **not** deleted (S-13). If the send fails definitively, the invite row is marked `revoked` and the unconfirmed user is cleaned up under the guard in 5.3.

### 5.2 `join-household` (Edge Function, service role, **unauthenticated**) and the Join page
- The link carries the token in the **URL fragment** (`/join#t=...`, S-6): fragments are never sent to servers, so Vercel access logs and referrers never hold the usable token (the earlier "logs contain `token_hash`" note was wrong). `/join` has a `vercel.json` rewrite, `Referrer-Policy: no-referrer`, the page reads the token then `history.replaceState` removes it, and analytics never records the fragment (test).
- A GET of the link (including a scanner prefetch) calls nothing and consumes nothing. The page's preview ("<owner> invited you as Editor") calls `join-household {action:'preview', token}`, which goes through `join_attempts` like a join and returns **only the owner's display name and the role** (S-9).
- **Every call (preview, join, and the recovery retry of 5.4) presents the token** (B-5); the function never accepts "a session for this email" or a pending-invite lookup instead.
- Order for a join: (1) insert a `join_attempts` row and rate-limit per IP and per `token_hash` **before any lookup**; (2) hash the token and find a pending, unexpired invite; on **any** failure (unknown, used, expired, revoked) return one constant generic error with the same shape and timing (T4); (3) **check the target account (B-4)**: `invited_user_id` user must have `lower(email) = invite.email`, no pending `email_change`, only the email identity, no MFA factors, no owned rows, and `household_status = 'invited'`; if any check fails, refuse with the same generic error, mark the invite `revoked`, clear `token_hash`, write a `security_events` row and tell the PM/owner (an attacker session changed the email, enrolled a factor or planted rows); (4) apply the **server-side password policy** (same minimum as sign-up, checked in our code because `admin.updateUserById` may bypass GoTrue's settings, S-14b; to be verified); (5) `admin.updateUserById(id, {password, email_confirm: true})`; (6) call `delete_user_sessions(id)` (sessions and refresh tokens); (7) write the profile name, insert `household_members`, set `household_status = 'member'`, mark the invite `accepted` and clear `token_hash` (single use), bump `household_state`; (8) sign in **server-side** with the password just set and return only the session (the password is never logged); the client applies it with `setSession`.
- **Accepted risk, stated plainly (T5):** anyone who gets the link can join as that invitee (for example a forwarded email). Controls: single use, fixed 7-day expiry, the owner can revoke at once, and the owner sees who joined. **Also accepted (S-14a):** an access token issued before the join still passes the plain `auth.uid()` policies on personal tables (`profiles`, `support_reports`, `create_handoff`) for up to 1 hour; it cannot read household data (members need a live session, section 3).
- `delete-my-login` takes the caller **only from the JWT** and is guarded to `household_status = 'former_member'` (S-14c).

### 5.3 Revoke, expire, resend
- **Revoke / expiry job:** set the invite status, clear `token_hash`; delete the auth user only under the guard checked inside the function right before the delete: `email_confirmed_at is null` AND owns no rows AND no membership AND `household_status = 'invited'` AND **no other pending invite exists for that user** (S-10); otherwise no-op. Same guard for every cleanup path. Test: a normally confirmed user with a stale pending invite is never deleted.
- **Resend (T2, S-8):** a **new** random token, overwrite `token_hash` in the same row, new 7-day expiry, same `invited_user_id`; the old link then fails (test); the mail is re-sent by our sender.

### 5.4 After a failure mid-way
`join-household` does steps 5 to 7 as one unit. If the tab closes after a successful call but before the client has the session, the invite is `accepted` and the user signs in normally with the password they chose; if the call failed before step 5, nothing changed and the same link still works. The earlier "recovery link" path is only for a user who is already a member and forgot the password (normal recovery); a recovery or any other retry that joins goes through `join-household` with the token (B-5).

### 5.5 Public sign-up (PRD check 16, F6)
"Create account" calls an Edge Function `signup-gate` that returns the **same answer** for a fresh address, an existing account and a pending-invite address: "Check your email. If you were invited to a household, use the link in your invite email." (a worded variant of the owner-approved check 16 copy that reveals nothing; the PM tells the owner as FYI). For a fresh address it performs the normal sign-up and confirmation mail; for the other two it does nothing. **This is UX only, not a security control** (anyone can call GoTrue sign-up directly); safety rests on 5.1 to 5.4. Rate-limited like invites. No auth hook is needed.
**Accepted enumeration risk (S-11):** an owner can learn "already invited" versus "has an account" for an address; limited by the attempt-based rate limits and the global per-email cap, reachable only by a signed-in owner.
**Rate limit (N7):** every attempt, including "already has an account", is counted before any existence lookup.

## 6. Triggers vs the client's whole-row upsert (B3)
- BEFORE INSERT: `created_by := auth.uid()`, `updated_by := auth.uid()` (client values ignored), `rev := 1`.
- BEFORE UPDATE: `new.user_id := old.user_id`, `new.created_by := old.created_by`, `new.updated_by := auth.uid()`; the revision check below; `new.rev := old.rev + 1`. (`ON CONFLICT DO UPDATE` sends client values, hence the pinning.)
- Tests: a client sending `created_by` = someone else or a different `user_id` is ignored/rejected; a member cannot write rows with `user_id = own id`.
- Backfill `created_by = user_id` runs in migration 1 **before** the triggers exist (S3), so no `updated_at`/`rev`/log is touched.

## 7. Concurrency and refresh (B2)
- **Compare-and-set:** the client keeps each row's `rev` and sends it back. The BEFORE UPDATE trigger raises `40001` ("stale") when `new.rev` differs from `old.rev`; the client maps it to PRD check 29 ("Updated by X. Please check and redo your change") and reloads that row. Old clients that omit `rev` send an unchanged value (no conflict); they lose the check until their stamped service worker updates.
- **Edits vs inserts:** the client no longer upserts rows it knows exist. New rows `insert`; known rows `update ... where id = ? ` (zero rows updated = "someone deleted this", **rejected, never re-inserted**). Deletes are `delete where id = ? and rev = ?`; zero rows deleted = already changed or deleted, shown as a conflict.
- **Merge (`cloud.js`):** after every poll merge, rebuild **both** `synced` and in-memory state from the merged server rows, otherwise the next diff would re-upsert others' rows or resurrect rows someone else deleted. A merge only runs when the save queue is idle; if there are unsaved local changes it is deferred.
- **Solo owners must not regress (R1):** the revision check inside the BEFORE UPDATE trigger runs **only when the owner has at least one active member** (`household_state.has_members`); solo behaviour is exactly today's. Updates use `return=representation` and the client stores the returned `rev` before the next operation on that row (the save queue never sends a second update for a row before the first returns). On `40001` the client refetches that row and, if the server row already holds the intended values with `updated_by = me`, treats it as success (lost-response retry). e2e: lost-response retry and rapid double edit on a solo ledger, and two tabs.
- **Cheap polling:** statement-level AFTER INSERT/UPDATE/DELETE triggers with transition tables bump `household_state.rev` for the distinct owner ids touched. The client polls just that one row on focus and every 30 s while visible and reloads only on change (also the hook for realtime later). Membership changes bump it too, so a role change or removal is noticed (PRD check 19, 20).

## 8. States (B8)
- **Discriminator (N2):** `profiles.household_status in ('owner','invited','member','former_member')`, set by `handle_new_user` (`owner`, or `invited` when a pending invite exists for the new email), by `join-household` (`member`) and by the remove/leave functions **and by owner account deletion (a before-delete function marks the members `former_member` first)**; `household_owner()` and `Cloud.load` both key on it (`invited` and `former_member` are never treated as owner and have no access, so neither an attacker session on an invited address nor a departed member can write rows or invite), so a brand-new owner with no rows is never mistaken for a departed member. Role changes, removals and data changes all trip the `household_state` counter (no `profiles.updated_at` trick).
- **Member leaves or is removed:** the membership row is replaced by a `household_former_members` row and `household_status = 'former_member'`; the login stays, with no ledger and no seed, and the app shows the "no longer have access" page. The page offers **Sign out** and **Delete my login** (Edge Function `delete-my-login`, `admin.deleteUser`, guarded to a `former_member` deleting their own login); approved by the owner 2026-11-04 (D1).
- **Owner deletes the account:** `household_members.owner_id` cascades, member logins remain without a household and see the same page; the owner's delete dialog explicitly lists the members and says they lose access.
- Former members' names: `household_people` includes `household_former_members`; `activity_log` stores an `actor_name` snapshot (B7).

## 9. Client (`prototype/`)
`cloud.js`: after sign-in compute `dataOwnerId` (`household_owner()`), `rowsFromData` sets `user_id: dataOwnerId` including **every composite upsert key** (S5: `manual_prices` `onConflict 'user_id,symbol,price_date'`; all other tables conflict on `id` only), settings read via `household_profile()`, `created_by/updated_by/rev` mapped in `dataFromRows`. Defaults that are about data (`defaultCatId`, onboarding key) follow the data owner; **`Analytics.identify` stays on the member's own auth id** with a new `household_role` property so members do not merge into one PostHog person (S4). Join view built on the existing recovery/`pwField`/consent pieces; `state.household = {owner, role, people}`; one `canWrite()` guard; `onSaveError` maps `40001` and RLS rejections to the PRD messages. Settings > Household card, Activity page (slice 2), row labels, "Added by / Edited by". i18n (`i18n-id.js`), `data-act`/`data-form`, analytics events and catalog.

## 10. Audit log (slice 2)
Per-table whitelist (`transactions`, `wallets`, `categories`, `budgets`, `debts`, `debt_payments`, `investment_accounts`, `holdings`, `holding_events`), row triggers writing `actor_id`, `actor_name`, owner, small `summary`. Skip no-op updates (`to_jsonb(old) - 'updated_at' - 'rev'` equals `to_jsonb(new) - ...`), skip sample-data rows and bulk statements (a statement touching more than 200 rows logs one summary row), and cap high-volume tables (`holding_events`, `debt_payments`: create and delete only).

## 11. Migrations (staging first; additive and backwards compatible; S3)
1. `household_tables`: tables, columns (`created_by`, `updated_by`, `rev`, `profiles.household_status`), functions, `household_state`, backfill `created_by = user_id` (no triggers yet). Migration 2 also applies the `profiles` column grants (B-3).
2. `household_rls`: replaces all policies (loop over `pg_policies`), defaults to `household_owner()`. **Ships with a down script** and its tests run against the **old client's request shapes** too.
3. `household_triggers`: created_by/updated_by/rev triggers; the `household_state` bump function is `security definer` (members cannot write that table) and, because transition-table triggers allow one event each, **three statement-level triggers (INSERT, UPDATE, DELETE) per table**, listed in the migration.
4. `household_functions`: updated views/functions, `handle_new_user` (sets `household_status` = `owner` or `invited`), `create_invite`, `delete_user_sessions`, `signup-gate`/`invite-member`/`join-household`/`delete-my-login` Edge Functions, member RPCs (membership itself is created only by the `join-household` Edge Function), expiry job.
5. (Slice 2) `household_activity`.
Each migration is applied to staging, SQL tests run, then production at release by Developer 2.

## 14. Security checklist
No secrets in the repo; service role only inside the Edge Functions; owner-only invite with attempt-based rate limit; generic existence error; single-use, 7-day join token that exists only in the email and in the URL fragment (never in `auth.users`, logs or referrers); membership only through `join-household`, which checks the target account; `household_status` not user-writable; instant revocation for members through the session check; minimal activity data; CSP unchanged; every new SQL function has fixed search_path and restricted execute.

## 15. Spike results (2026-11-04, staging, real GoTrue) and pending owner decisions
Method: a temporary Edge Function on staging (restricted to the staging smoke account; now replaced by a stub that returns 410), real calls from the sandbox, all spike users and data removed (0 left, no orphan rows). **Caveat: staging has email auto-confirm ON; production presumably confirms by email, so F2 was not reproduced for production. The design below does not depend on that difference.**
- **F1 (e) `handle_new_user` fires at invite time.** `generateLink`/invite created an unconfirmed user and seeded a profile, 1 wallet and 23 categories at once. So the skip-seeding rule for pending invites is required, not optional.
- **F2 (a) public sign-up on an invited, unconfirmed email.** With auto-confirm it **returned a signed-in session for the invited account immediately**, stored **no password** (password hash stayed empty), and **burned the invite token**: the real invitee's link then fails with `otp_expired`. So anyone knowing the address can hijack or break an invite. Consequence: do not rely on GoTrue's invite token (our own join token, section 5) and revoke old sessions at join.
- **F3 (d) password overwrite.** `admin.updateUserById` sets the invitee's password, after which the attacker's refresh token was `refresh_token_not_found` (revoked) and the attacker's password (never stored) did not work; the invitee signed in with the new one. An already issued access token can live up to 1 hour, hence the session check in `household_owner()` (section 5).
- **F4 (b) invite edge cases.** Invite on a confirmed address: `422 email_exists` (maps to the PRD check-2 message). Fresh address: works. Re-invite while still unconfirmed: succeeds with the **same user id** (acts as resend). Delete then invite again: works with a new user id (the revoke path frees the address).
- **F5 (c) server-side `verifyOtp` with a valid invite token** could not be tested because F2 burned it; not needed any more (own token).
- **F6 (f) auth "before user created" hook** is not needed: public sign-up goes through `signup-gate` with one generic answer (section 5.5); UX only.
- **Still to run before slice 1 (spike 2, owner actions through the PM):** (i) the owner switches **"Confirm email" ON for staging for about an hour**, and checks production's real setting in the dashboard; (ii) repeat F2 with confirmation ON; (iii) verify whether `admin.updateUserById` applies GoTrue's password policy; (iv) verify that `auth.refresh_tokens` rows go with the `auth.sessions` delete and the exact `session_id` claim name; (v) paste the Resend secret (`RESEND_API_KEY`) as an Edge Function secret for staging and production and confirm the sender address; (vi) real end-to-end invite to a `+alias` inbox with our own mail.
- **Not tested:** the real invite email rendering and delivery with the new template (needs the owner to paste the template into the Supabase dashboard); behaviour with email confirmation ON (optional repeat if the owner turns "Confirm email" on for staging for an hour). Three test emails were sent to the owner's `+alias` inbox; the owner may delete them.
- **D1 (decided 2026-11-04):** the owner approved "Delete my login" (PRD v2.1).
- **D2 (decided 2026-11-04):** the owner approved the change: PRD check 16 now reads "Check your invite email", no account or password is created for an email with a pending invitation; membership only from the invite link. Detection at sign-up time is still to be designed (see F6).
